# 测试套件整合评估（2026-10-16）

有必要整合执行入口、夹具和重复扫描，但目前没有证据支持按总数量大幅删除测试。先减少没有额外验证价值的工作，再建立可靠的分层选集；安全、持久化和研究资格的不同失败边界仍须保留。

## 1. 实际规模与耗时

基于2026-10-15最后一次完整Python验收的JUnit分析。本轮调查开始时，1,371个已验收源码、测试及配置文件的摘要与该次验收一致。以下全量数据是历史实测，不是本轮重新跑全量的结果。

| 指标 | 结果 | 含义 |
| --- | --- | --- |
| Python测试文件 | 513 | 文件较多，但按领域及失败边界拆分本身不是浪费 |
| 测试函数定义 | 6,442 | 参数展开后为12,036个收集项，另有57个子测试 |
| 全量耗时 | 1,087.954秒，约18分08秒 | 包含覆盖率插桩；用例时间合计1,052.429秒 |
| 单个用例中位耗时 | 0.005秒 | 大多数用例很轻 |
| 最慢25项 | 443.397秒 | 占记录用例时间42.1%，比删大量快用例更值得优化 |
| 最慢136项 | 657.048秒 | 只占用例数1.13%，占记录用例时间62.4% |
| `test_frontend_*.py` | 938项，51.608秒 | Python中的前端行为测试不是18分钟的主要来源 |
| `test_workspace_backup*.py` | 307项，20.330秒 | 数量多，但总耗时有限，失败隔离价值高 |

JUnit用例时间可以包含夹具和收尾，不能直接解释为被测API响应时间。单次历史慢记录也不能证明稳定瓶颈。

浏览器当前收集为51个spec、每个项目159项，四项目展开636个身份；项目为桌面/移动Chromium、桌面Firefox、桌面WebKit。最近完整记录（2026-10-15）为586通过、50项条件跳过、无失败或flaky，共596.6秒。它不是636个互不相关的业务场景。本轮只复核收集结果，没有重跑该浏览器矩阵。

同分反例的模块夹具使用55个交易日、200只股票、4个候选，生成11,000条价格记录，并触发合计11次账户回放。它检验的是实际统计陷阱；整合应减少重复构建，不能只以减小数字换取速度。

## 3. 不应依据数量直接删除的部分

- 线程竞争和跨进程文件锁保护不同边界，不能互相替代。
- SQLite复制前容量检查与复制中增长检查不同；旧目标恢复回滚与新目录失败清理也不同。
- 相同测试函数体可能使用不同参数。评分的缺失流动性矩阵与非法行情矩阵就是这种情况，不能用文本相似度自动去重。
- 前瞻计划冻结、截止后不补采、请求不得重复提交、源码漂移拒绝执行等是资格约束，不应因当前生产尚未触发就删除。
- mock浏览器表单测试与真实`api.js`/FastAPI/SQLite/重启持久化集成验证不同层，不能用一方代替另一方。
- 上海时区选集只有6个模块117项，它在UTC全量之外验证真实环境差异；不属于无意义的重复运行。

AST调查只找到两组较长的相同函数体，其中一组参数不同。这个结果不证明没有语义重复，但不支持“大量测试可以直接删除”的判断。

## 4. 不能误判的慢测试

`test_minute_retention_event_time.py`的HTTP用例在历史全量记录68.947秒，但其夹具只有11条分钟记录和1条日线，没有主动sleep。本轮原样独立运行：

| 条件 | 用例call耗时 | pytest总耗时 |
| --- | --- | --- |
| 不开启覆盖率 | 0.04秒 | 0.95秒 |
| 同全量的app/tools覆盖率插桩 | 0.05秒 | 4.16秒 |

其全量慢记录的根因尚未定位，后续需要检查运行顺序、共享状态或资源等待。本轮没有把它改为跳过，也没有删除它。局部覆盖率诊断使用独立临时数据文件、不生成报告，且不对单个用例施加全仓90%门槛；工程配置中的90%门槛未改。

## 5. 建议的执行分层

| 场景 | 执行范围 |
| --- | --- |
| 日常局部迭代 | 相关静态检查、受影响领域测试、相关Chromium流程；不声称全仓覆盖率通过 |
| 当前PR验收 | 保留一次完整Python覆盖率，按变更范围运行浏览器与真实前后端集成；先消除无效重复工作 |
| 共享基础设施或跨域变更 | 完整Python、时区选集、相关浏览器矩阵与真实集成；未知影响范围回退全量 |
| 正式完整交付 | Python全量及90%覆盖率、四浏览器、真实集成、上海时区、Node24兼容和安全工作流 |

当前没有注册可靠的`fast/unit/integration` pytest分层标记，也没有经验证的“修改文件→全部受影响用例”映射。不能直接用一个不存在的`pytest -m fast`入口，或仅凭同名文件选测试后宣称完整验收。也不建议为了本次整合立即引入未经验证的全并行运行：进程、端口、锁和全局状态测试需要先验证隔离性。

CI每个quality作业只运行一次UTC全量。现已按工作流名称、事件类型和ref添加concurrency控制，新运行取消同组的过时运行；这遵循[GitHub官方工作流并发语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)。`push`与`pull_request`仍同时启用且分组隔离，PR分支推送仍可能触发两组工作流。本次未改触发范围，保留上海时区选集和Node24兼容检查；跨事件去重需要另行结合仓库分支策略处理。

后续整合的验收标准应是：原风险场景仍有明确测试归属、收集身份没有意外丢失、故障能被原断言检出、目标模块耗时确实下降；最后才用一次完整验收衡量总体变化。不要以把12,036项缩成某个任意整数作为目标。
